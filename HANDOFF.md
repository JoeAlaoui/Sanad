# HANDOFF SANAD — état au 09/11/2026 (lot 14 : données en SQLite)

## 1. Produit
SANAD = application web locale de pilotage du Helpdesk SI de l'AMMPS (Agence Marocaine du Médicament et des Produits de Santé), DSID. Multi-utilisateurs, multi-volets, JSON uniquement.
- **Tarkhiss** : Support Email & Hotline (saisie appels/emails par jour, analyse mensuelle, dashboard, vue annuelle, prompts Copilot, rapport email/PDF/Excel).
- **Moussanada** : Helpdesk GLPI (import tickets agrégés CSV/direct API GLPI, dashboard, analyse & Copilot, vue annuelle, guide GLPI).
- **Reporting Métier PCHC** (sous-volet de Tarkhiss dans la sidebar) : import Excel 5 feuilles, dashboard, analyse, exports Excel/CSV/PDF/PPTX « Revue Direction », email avec Excel joint.
- Transverse : Administration, Utilisateurs, Notes, Base de connaissances, Qualité des données, SOP & preuves d'audit, Sauvegardes.

## 2. Historique résumé
Application d'origine livrée par lots (legacy). Puis migration vers React 19 + TS + Tailwind v4 + shadcn/ui (lots 2 à 9, avec pages Qualité, Sauvegardes, SOP, dashboards « copie carbone »). **Décision de Youssef (20/10/2026) : l'ancienne interface est meilleure → retour à la legacy, React/shadcn SUPPRIMÉ, et les nouvelles fonctions portées dans la legacy.** (lot 10). Les anciennes pages React n'existent plus dans le code.

Routes utiles : `/api/<module>/month/<ym>`, `/calls/<ym>`, `/emails/<ym>`, `/analysis/<ym>`, `/settings`, `/months-list`, `/last-sync`, `/alert-history`, `/preview-email/<ym>`, `/send-email/<ym>` (payload to, cc, greeting, charts ; crée le .eml + log d'envoi), `/export-pdf/<ym>`, `/export-xlsx/<ym>`, `/api/system/network-info|network-config`, `/api/admin/*` (audit-log, rgpd search/anonymize, glpi test/import, snapshots, sop, audit-pack), `/api/quality/overview`, `/api/notes`, `/api/knowledge`.
UI : `activateTab(tab)` → `renderTab(tab)` ; modules via `#moduleSwitch` et `switchModule` ; mois global `#monthSelect` (`loadMonth` Tarkhiss / `loadMoussanadaMonth`) ; `state`, `mState`, `moduleSettings`, `globalSettings`, `currentUser`.

## 4. Fonctionnalités par rôle
- **admin** : tout (saisie, import, envoi email, administration, utilisateurs, sauvegardes, SOP, RGPD, GLPI direct, partage réseau, journal d'audit).
- **superviseur** : lecture seule des dashboards/vues annuelles/exports (Excel, PDF), comparatifs N-1, Qualité des données. Pas de saisie, envoi, admin.
- **hotliner** : Notes + Base de connaissances (volets assignés) ; Tarkhiss en lecture limitée.
Topbar legacy : fil d'Ariane, ★ favori, mois ←/→, recherche globale, indicateur de sauvegarde et de synchro, rôle, « Partager SANAD » (admin), « Compact », « ? Aide » (onboarding par rôle), déconnexion.

## 5 bis. Lot 11 — Reporting Métier PCHC : import brut + livrables (28/10/2026)
- `pchc_raw.py` : `parse_workbook()` (pur, openpyxl read_only, en-têtes ligne 5, colonnes détectées par en-tête avec repli B/H/J/F/D, rapport : lignes, feuilles manquantes/vides/ignorées, statuts inconnus, coquilles, contrôle de signature des colonnes → **bloquant**, forçable) et **`pchc_compute()`, calcul unique** (sémantique COUNTA/NB.SI insensible à la casse/SOMME.SI des formules Excel) utilisé par Excel, PPTX, PDF, e-mail et UI. - `pchc_excel.py` : **copie conforme par gabarit**. À chaque export, `_TemplateWriter` réécrit seulement les feuilles brutes, les `<v>` des formules (format Excel : 17 chiffres, notation E sous 0,1, SOMME séquentielle), les caches des graphiques et la date ; tout le reste (16 graphiques, styles, MFC Excel 2010, mise en page) est identique **à l'octet**. Seul écart voulu (décision Youssef) : le classeur s'ouvre sur le Dashboard, et non sur le dernier onglet consulté dans la référence. Les valeurs de chaque cellule viennent de `_Builder` (port openpyxl de `reference/build_dashboard_pchc_reference.py`, aussi utilisé en repli si le gabarit manque). Version allégée : feuilles brutes et calcChain retirées, formules qui les lisaient → valeurs. Si la référence change : relancer l'outil puis les tests. Pourquoi pas XlsxWriter/openpyxl : ils ne savent pas reproduire le XML des graphiques et MFC enregistrés par Excel.
- Import : le classeur de référence complet s'importe tel quel (feuilles « KPI … »/« Dashboard » ignorées, noms exacts prioritaires).
- `pchc_deliverables.py` : modèle hybride charte AMMPS + couleur par volet. PPTX 16:9 (9 diapos : garde, synthèse, chiffres clés & alertes, 5 KPI, méthodologie), PDF A4 paysage (WeasyPrint, repli xhtml2pdf, « Page n / N »), corps e-mail, `.eml` multipart/mixed (X-Unsent: 1, RFC 2231).

## 5 sexies. Lot 14 — Migration JSON → SQLite, par étapes (décision Youssef du 09/11/2026)
Motif : usage sur plusieurs années, données en croissance continue (tickets bruts, séries, sources, journaux). Règle « JSON > base de données » **révoquée**. Principe : couche d'accès unique `store.py` (clé = chemin du document), puis changement de backend derrière elle, sans toucher aux appelants ; JSON conservé comme repli et pour le retour arrière.
- **Étape 1 — FAIT** : `store.py` (backend fichiers : `read_json`, `write_json` avec sauvegarde horodatée + écriture atomique + verrou, `remove`, `exists`, `names`). `app.py` : tous les chargeurs/écritures de documents passent par `store` (`write_json_safely` = enveloppe), `ops.py` : listes de mois via `store.names`. Test : `tests/test_store.py` ; les 5 autres scripts de test restent verts.
- **Reste hors `store`** (à traiter aux étapes suivantes) : journaux append-only (`audit_log.jsonl`), sauvegardes/restauration/snapshots ZIP de `data/` (`ops.py`), fichiers binaires (exports `.eml`/PDF, `raw_imports/`, logos, `.secret_key`, `users.json`), `pchc_excel` (méta du gabarit statique).
- **Étape 2 — FAIT** : `store.py` a deux backends interchangeables (`SANAD_STORE=json` par défaut | `sqlite`, fichier `data/sanad.db`, WAL). Schéma : `docs` (un document JSON par clé = chemin relatif à `data/`), `docs_history` (ex-.bak, rétention 20 par clé), `tickets` (1 ligne par ticket brut, index mois/statut), `journal` (audit_log.jsonl). Interface : `read_json/write_json/exists/remove/names/mtime/latest_mtime/append_jsonl/read_jsonl/export_documents/snapshot_to/close/reopen`. Branchés : audit (`log_audit`, `/api/admin/audit-log`, dossier de preuves), `last-sync`, `export-all`/`import-all` par volet, snapshots ZIP (copie cohérente de la base via l'API de sauvegarde SQLite, restauration + réouverture). `tools/migrate_json_to_sqlite.py` (version de base : copie les documents + le journal, vérifie l'égalité, ne touche jamais aux JSON). Tests : `test_store.py` (2 backends), `test_store_ops.py` (snapshot/restauration/archives), et les 5 scripts existants verts en json ET en `SANAD_STORE=sqlite` (le serveur de test migre ses données de départ).
- **⚠ Ne pas activer `SANAD_STORE=sqlite` sur les données réelles avant la fin de l'étape 3.** Non couvert : restauration d'un snapshot « ère JSON » dans une instance sqlite (et inverse), historique des tickets bruts (pas de version précédente en sqlite, les snapshots ZIP servent), mesures de volumétrie.
- **Étape 3 — FAIT** : (a) `tools/migrate_json_to_sqlite.py` durci : validation de TOUS les JSON avant d'écrire (aucun écrit si un fichier est illisible), base temporaire `sanad.db.migrating` renommée seulement si tout est vérifié, refus si `sanad.db` existe, `--dry-run`, `--report`, contrôles (document par document, journal en ordre, nombre de tickets, totaux des séries mensuelles), rapport par dossier. (b) `tools/compare_backends.py` : même copie de `data/` servie en JSON et en SQLite, 47 réponses d'API comparées → identiques (corrigé au passage l'ordre non déterministe des catégories à égalité dans `category-trend`). (c) Restauration d'un snapshot d'un AUTRE mode refusée avec message clair (`ops.restore_zip`). (d) Accès filtré aux tickets : `store.tickets(path, start, end, open_only)` / `tickets_count`, repris par `load_raw_tickets(start, end, open_only)` — branché sur retards (ouverts seulement), analytics/export par période, rapport mensuel (un mois), annuel, heatmap. (e) `tools/bench_store.py` : à 82 750 tickets (×50), lecture des tickets ouverts 47 ms (SQLite) vs 404 ms (JSON), un mois 81 vs 378 ms ; lecture complète 498 vs 400 ms et écritures complètes équivalentes (SQLite n'accélère que les lectures FILTRÉES) ; base ≈ 13 % plus grosse que les JSON. Répétition réelle faite sur une copie de `data/` : 85 documents, 114 entrées de journal, 1 655 tickets, 0,7 s, vérifications OK. Tests : `test_migration.py` ; les 8 scripts verts en json ET en sqlite.
- **Étape 4 — FAIT le 09/11/2026 : SANAD tourne en SQLite sur le poste de Youssef.** Base : `~/sanad-data/sanad.db` dans WSL (système de fichiers Linux : sur `/mnt/d` (9p) SQLite fonctionne mais chaque écriture coûte ~17 ms au lieu de ~0). Ne pas utiliser `data/` comme source de vérité. Les fichiers (exports .eml, imports bruts, logos, `_snapshots`, `.secret_key`) restent dans `data/`. Les snapshots ZIP contiennent une copie cohérente de la base (`data/sanad.db`).
- **Retour arrière en JSON sans perdre les écritures récentes** : arrêter le serveur ; `.venv/bin/python tools/export_sqlite_to_json.py data /mnt/d/Apps/sanad_data_export --db ~/sanad-data/sanad.db` ; vérifier ; remplacer les documents de `data/` par ceux de l'export (garder l'ancien dossier) ; relancer SANS `SANAD_STORE`/`SANAD_DB_PATH`.
